# Captain wakeup shutdown ownership

Captain wakeups now stop final admission synchronously and join accepted raw message deliveries before SQLite close. Each delivery is registered before invoking the host; shutdown can cancel a queued send without starting it. Active sends remain owned through bounded close failure and retry. Every project delivery is joined, stale timer callbacks avoid database reads, and closed owners cannot restart. Reusable `stop()`/`start()` remains available before final shutdown.

The existing 19 wakeup/event/helper regressions run under standalone Node with portable SQLite where required. Five lifetime controls exercise the actual project event bus and database with fixture agent sends: late writes after failed close, queued-send cancellation and stale timer delivery, two simultaneous project sends, reusable stop and deadline validation, and handled raw rejection. These establish scheduling ownership without a real model call or installed production Captain claim.

Application teardown closes admission before stopping agents and joins the owner alongside other raw service drains before SQLite close. [Local evidence](evidence/captain-wake-owner-local.json) records source/report hashes and exact validation. Scheduled coordination, heartbeat, recurrence and workspace cleanup require separate shutdown/native-host work in [#212](https://github.com/krazyjakee/21x/issues/212) / [#208](https://github.com/krazyjakee/21x/issues/208). Production provider/renderer integration and G2/G3 acceptance remain open.

Final local validation passed 1,281 complete standalone/private-pipe cases with zero skips in 87 files and 5,299 application assertions with 20 optional skips in 381 files. The application command exited zero with no unhandled errors. Forced typecheck, changed-source lint, contract freshness and desktop/mobile build passed. Durable profile import recovery now has an explicit 15-second test deadline: retained earlier runs show completed SQLite/fsync cases exceeding the default five seconds under both four and two workers. All durability, preservation and production bounds are unchanged; this is no profile migration performance acceptance.
