# Copied-profile record credential conversion

The rehearsal converter now covers the JSON string fields protected by the actual DatabaseManager adapter, in addition to secret BLOBs, API-key settings, OAuth tokens and connector auth. It uses the existing `21x-record-credential:v1:21x-credential:21x.aes256gcm.v1:` representation and the supplied authenticated-profile provider; it introduces no new cipher, storage format or schema.

| Stored column | Exact protected leaves |
| --- | --- |
| `agents.config` | Every existing string value in `api_keys`, including inactive historical vendor keys |
| `mcp_servers.headers` | Every existing dictionary string value, matching the actual record adapter |
| `mcp_servers.environment` | Every existing dictionary string value, matching the actual record adapter |
| `mcp_servers.oauth_metadata` | `client_secret` |
| `task_sources.config` | `client_secret`, `access_token`, `api_token`, matching the adapter's stored union |

`RehearsalOptions.recordInterpretations` is a trusted exporter manifest of exact table, row ID, column and JSON path. Every nonempty protected leaf needs explicit `plaintext-utf8` or `authenticated-record` provenance. The latter requires the exact original authenticated format and decoder; a prefix alone never establishes provenance or selects a provider. Plaintext declarations containing a reserved record envelope are refused. Unknown versions, wrong or missing keys, incomplete/duplicate/stale manifest entries and nonstring protected fields fail visibly. Native API-key setting envelopes remain outside the legacy setting importer and are refused rather than double-wrapped as guessed plaintext; ordinary noncredential setting values remain unchanged. Empty string clears remain byte-identical and need no conversion. The actual field is snake_case `client_secret`; the converter does not reinterpret arbitrary credential-like aliases or suffixes.

The source snapshot retains the existing canonical temporary-fixture marker, held profile lock, stopped-old-owner requirement, WAL checkpoint, exclusive SQLite transaction, immutable authenticated backup capsule and bounded resource manifest. Sources may be synthetic or supported copied fixtures; the API has no live-profile mode. Missing historical tables or optional metadata columns are not invented by conversion. This limited structural compatibility is not evidence for every supported historical schema or installed profile.

SQL checks row counts, identifiers, field sizes and aggregate input sizes before JSON materialization. Existing reviewed bounds remain 10,000 credential records, 1 MiB source record/column, 16 MiB input and 32 MiB encrypted output; the rehearsal profile cap remains 8 MiB. The lexical JSON walk also caps nesting at 64 and nodes at 100,000. Valid larger historical profiles require separately reviewed bounds and evidence; refusal leaves their source bytes intact. Duplicate decoded keys, including escaped equivalents, are rejected rather than silently discarded by JSON.parse.

Conversion replaces only protected string tokens. Whitespace, property spelling/order, escaped keys, number representation, nested unknown metadata and every noncredential column remain unchanged. A preservation hash neutralizes only the exact converted leaves, never entire JSON columns. It still covers row IDs/rowids, schema/index/trigger definitions, SQLite sequence state, noncredential fields and declared resource hashes. The candidate transaction checks every exact planned envelope after all writes, so a trigger cannot swap another credential under the preservation mask. SQLite normalization runs in RAM and rejects changed row identities. Published candidate pages no longer retain legacy plaintext credential cells.

The encrypted journal binds the exact record interpretation/path manifest by a stable digest. Recovery cannot accept a different declaration merely because the original source and noncredential rows match. Old journals without this field remain compatible only with an empty record manifest. Interrupted preparation/publication resumes from the authenticated immutable original and journal, and validates candidate integrity, preservation and bytes before acceptance. Candidate/journal/backup tampering fails closed. Original database and declared resources are never replaced.

A rollback file is permitted only when the original credential representations were already protected. If any JSON field or other credential originated as plaintext, the original remains available inside its authenticated capsule and a plaintext rollback database is refused. This is a rehearsal rollback boundary, not a reverse migration for a live profile. New application writes and accepted external effects would require forward repair or an explicit reverse-migration plan; restoring a backup must never silently discard them.

Authored tests cover all protected JSON classes with actual SQLite and authenticated transformations, exact noncredential representation/empty-value preservation, prototype-named fields, malformed/duplicate JSON, complete trusted provenance, unavailable/wrong owners, source bounds, trigger swaps, journal interpretation changes, interrupted publication and protected-original rollback. The integration fixture opens a copied candidate through actual DatabaseManager readers, verifies agent/MCP/source credentials and retained task/project/resource/session references, performs format-aware writes, reopens again and rejects a tampered record envelope. Provider keys in these tests are synthetic in-memory keys; this is not real OS-store or installed-app evidence.
