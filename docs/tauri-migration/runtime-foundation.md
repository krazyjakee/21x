# Tauri runtime foundation (T01 preparation)

Status: experimental implementation. The Linux debug Debian package has compiled and passed its installed GUI/runtime smoke; other targets and full T01 feasibility remain unverified. This work does **not** complete T01, accept G0, or migrate the domain engine. The existing Electron application remains the production host.

The isolated Tauri 2 executable starts a staged standalone Node by absolute resource path. Startup requires an `engine.initialize` response before opening the small feasibility screen. The screen can call `engine_status` and `engine_invoke` with an empty payload for `engine.ping` or `engine.probe` only. No task/database/secret API is exposed. The probe creates a temporary in-memory SQLite table, launches a tiny Node PTY, forks this service file in worker mode, and imports two representative agent SDKs without making API calls. Each failed check is reported explicitly; `ok: false` is not a successful feasibility result.

## Resource contract

The coordinator stages these ignored paths with `pnpm tauri:prepare`:

| Source staging path | Runtime lookup |
| --- | --- |
| `src-tauri/resources/node/node` (`node.exe` on Windows) | `resource_dir/resources/node/node[.exe]` |
| `src-tauri/resources/service/feasibility.mjs` | `resource_dir/resources/service/feasibility.mjs` |
| `src-tauri/resources/service/node_modules` | Adjacent to the service entry, normal Node package resolution |
| `out/tauri-renderer` | Bundled standalone feasibility frontend |

Missing resources fail startup; there is no system Node fallback. The bootstrap response must report the staged runtime pin **Node 22.23.2**. Rust canonicalizes resource/profile roots, rejects executable/entry paths outside the resource root, and checks executable permission bits on Unix. Staging must preserve executable permissions and contain native addons compiled for the bundled standalone Node ABI and target OS/architecture. Existing Electron native binaries must not be treated as compatible. No dependencies, runtime executables, or copies of node_modules are committed. Tauri resource mapping and its build script are responsible for copying staged resources into development and packaged layouts. This layout follows [Tauri resource documentation](https://v2.tauri.app/develop/resources/); packaged executable bits and signing still need platform evidence.

## Protocol and lifecycle

Every UTF-8 NDJSON envelope has `protocolVersion: 1`, `engineEpoch`, and `kind`. Requests carry a monotonically increasing `host:N` request ID, operation, and payload. Responses carry the same ID and exactly one of result/error. Initialize uses an empty epoch and payload `{protocolVersion: 1, profileRoot, resourceRoot}`; the host adopts the random epoch from the matching successful response. Subsequent frames must match it. The service verifies initialize roots against its host-injected environment. There are no service-to-host callbacks in this spike.

Input and output frames are bounded to 1 MiB excluding LF, pending/active requests to 128, queued output bytes to 4 MiB, and operation/write-stall deadlines to 30 seconds. The service uses a fixed frame accumulator, validates nesting to 64 levels, and rejects invalid UTF-8 and byte-order marks. Partial/multiple reads are supported. Rust assigns request IDs under the writer lock, preserving monotonic wire order under concurrent calls. Timeout/cancellation releases pending slots and sends an `engine.cancel` event after a complete write; dropping an incomplete write invalidates framing and disconnects the engine. Handler capacity remains reserved until the underlying Node operation settles even when its response deadline/cancellation wins. Synchronous native calls remain uninterruptible within Node; host disconnection can terminate the process. Stale responses and cancellation events are ignored. Malformed/oversized input, version mismatch, duplicate IDs, and stream loss terminate the service rather than continue with ambiguous state. This experimental duplicate-ID policy is deliberately stricter than the shared peer's error response. Errors use fixed redacted messages. The host discards the child's stderr; the service replaces dependency console methods with redacted diagnostics. Domain log sinks will need a separate design.

The service never opens a real profile, registers production OAuth schemes, or reads credential/environment configuration. Rust clears inherited environment before spawning Node, preserving only Windows runtime/temp variables and injected isolated paths. Workers receive the same small OS environment and no arbitrary parent configuration. A second simultaneous probe is rejected to avoid multiplying native work.

On quit, Rust requests shutdown and allows the child to exit within a three-second grace period, rejects remaining requests, kills/reaps its owned direct child when needed, and waits up to five seconds. Repeated exit requests remain blocked until the drain completes. Node cancels pending probes and kills owned PTY/worker children when its stdin closes or shutdown/signals arrive. Abrupt host death and Windows process-tree termination are **not yet platform proven**; this foundation makes no claim of a production parent-death/process-tree guarantee. There is no automatic restart or mutation replay.

## Permissions and identity

The experimental identity is `com.krazyjakee.21x.tauri-feasibility`; only its own app-local data `feasibility` directory is created. The host never resolves the Electron profile. No migration or cross-host profile locking is needed until a later shared-profile implementation.

Custom commands are included in `AppManifest::commands` to generate command ACLs, then granted only to the local `main` WebView capability. This is required because [Tauri custom commands are otherwise allowed by default](https://v2.tauri.app/security/capabilities/). Rust additionally checks WebView label and exact permitted origin. Navigation is restricted to packaged app origins without custom ports (or localhost:1420 in Tauri development mode); new windows, downloads, and WebView permissions are denied. CSP forbids embedded frames and remote resources. No shell, filesystem, remote capability, or browser panel is registered. Packaged malicious-origin/native-command checks remain outstanding.

## Batch validation

Installation, tests and compilation were deferred during parallel editing and then run centrally. [Implementation status](implementation-status.md) records the results and remaining platform gaps. Run batch checks sequentially:

```sh
node --test --test-concurrency=1 src/service/feasibility.test.mjs
pnpm tauri:prepare
pnpm tauri:frontend:build
CARGO_BUILD_JOBS=1 cargo test --locked --manifest-path src-tauri/Cargo.toml -p twentyonex-engine -- --test-threads=1
TWENTYONEX_TEST_RESOURCES="$PWD/src-tauri/resources" CARGO_BUILD_JOBS=1 cargo test --locked --manifest-path src-tauri/Cargo.toml -p twentyonex-engine -- --ignored --test-threads=1
# Requires the platform WebView development libraries:
CARGO_BUILD_JOBS=1 cargo check --locked --manifest-path src-tauri/Cargo.toml -p twentyonex-tauri-feasibility
```

The subprocess tests are dependency-free and cover fragmented/coalesced frames, initialize/ping/shutdown, root validation, stale epochs, malformed/oversized/truncated frames, UTF-8 errors/BOM, JSON depth, cancellation IDs, duplicate IDs, and real-file fork execution. The GTK-independent `twentyonex-engine` crate contains the actual supervisor, three unit tests and four opt-in staged-Node tests. These exercise startup, concurrent wire ordering, queued cancellation, and shutdown/reaping. Its `probe` example runs the native checks after standalone-native staging without building a GUI host.

Direct Rust dependency versions are pinned to Tauri 2.12.3, tauri-build 2.7.2, Tokio 1.53.2, Serde 1.0.229, and serde_json 1.0.154, verified against crates.io metadata. Cargo.lock is generated and checked in; Rust 1.90 is the declared source minimum and local core validation used 1.98. Supported GUI platform prerequisites, macOS Node signing, Windows executable inclusion, packaged native addon layout, clean machines with Node absent from PATH, all four architecture builds, and packaged shutdown/crash evidence remain T01 blockers.

Full service extraction, schedulers, shared-profile locking, credentials, browser retirement/data compatibility, and production host services belong to later cards and must not be inferred from this screen.

## Remote Linux native verification

The manually dispatched `Tauri native Linux feasibility` workflow installs the [official Linux WebKitGTK prerequisites](https://v2.tauri.app/start/prerequisites/) on Ubuntu 24.04, pins Node 22.23.2 and Rust 1.98.0, stages standalone native modules, and builds a debug Debian package with the locked Rust dependency graph. Cargo/native builds use one job, incremental builds and debug symbols are disabled, and only compressed Cargo dependencies are cached. Compact evidence and the larger Debian package are uploaded separately with seven-day retention, so reviewing JSON/logs does not download the package. The workflow has no release publication step and does not run automatically for each commit.

The [first remote run](https://github.com/krazyjakee/21x/actions/runs/38266143269) compiled the real Linux native host, built the Debian package, and passed all five headless native probes. GUI launch was not part of that first run. No heavy native validation was run locally in this workstream.

The installed-package smoke now installs that Debian package on the ephemeral runner and launches `/usr/bin/twentyonex-tauri-feasibility` under Xvfb and a D-Bus session. Host PATH is `/nonexistent`; it resolves Node and the service from Tauri's installed `/usr/lib/...` resources. Its XDG roots are temporary runner directories. The debug-only `TWENTYONEX_NATIVE_SMOKE_REPORT` opt-in records a finished WebView load, a real renderer-to-host ping, rejection of `engine.shutdown` by the explicit operation allowlist, denial of attempted remote navigation, all five native probes, a native window-close event, and engine unavailability after shutdown. A separate workflow check confirms the resource/profile roots and scans processes for that exact isolated profile marker or installed Node executable after exit. This establishes absence of a surviving owned running process; it does not independently prove OS-level child reaping.

The smoke report is diagnostic metadata, not a product API. Release builds ignore its enabling environment variable. The renderer cannot enable smoke mode or choose report paths, and its optional receipt is accepted only when a trusted developer/CI environment already enabled that mode. Missing callbacks and failed probes produce a failed report/nonzero exit, with bounded watchdog and workflow deadlines.

This proves only the exercised Linux debug package when a successful smoke report exists. The trusted WebView command success and explicit operation rejection do **not** establish Tauri capability denial across untrusted/remote WebViews. Cross-WebView ACL attacks involving untrusted artifact frames, release signing, AppImage/macOS/Windows installs, and abrupt parent-death/process-tree behavior remain separate gates. Do not close #197 on the first compile-only report; review the installed GUI smoke outcome first.

The [installed-package run](https://github.com/krazyjakee/21x/actions/runs/38267769673) passed at source revision `0946d24775917201d6389bc713dced198058cdaf`. The checked-in [smoke report](evidence/linux-x64-installed-gui.json) records all exercised checks and no surviving owned process. Ubuntu 24.04 used GTK 3.24.41, WebKitGTK 2.52.6 and librsvg 2.58.0. These are observed versions, not accepted minimum platform requirements. The compact evidence artifact contains logs, checksums and a separate headless report; the debug Debian artifact is a feasibility package, not a published release.

## Packaged target matrix (T01)

The manual `Tauri packaged platform feasibility` workflow runs macOS x64 on `macos-15-intel`, macOS arm64 on `macos-14`, Windows x64 on `windows-2022`, and Linux x64 AppImage on Ubuntu 24.04. Its matrix uses one platform at a time and one Cargo/native build job. The optional `target` choice permits retrying only a failed target without rebuilding successful packages. Compact logs/reports remain separate from DMG/NSIS/AppImage artifacts, with seven-day retention and no publication step.

`scripts/tauri-packaged-smoke.py` mounts each DMG and copies its real app bundle to a temporary installation, silently installs NSIS into a temporary directory, or extracts an AppImage and executes its AppRun launcher. It does not inject development resource paths. The debug host hides system Node from PATH before spawning the engine; package launchers retain the tools they need to reach main. An explicit debug-only temporary profile override handles platforms whose profile lookup ignores XDG variables. The host observes native close and then requests quit explicitly for platforms that keep an application alive after its final window closes.

Each report must prove trusted UI load/invoke, operation restriction, denied remote navigation, all five native probes on the expected architecture, actual resources beneath the installed/extracted package, isolated profile roots, and no surviving process using the exact packaged Node executable. Windows extended-length paths are normalized before comparisons. Linux observes `/proc`, macOS observes the mapped executable with `lsof`, and Windows uses Win32_Process executable paths. These observations do not kill processes by generic names or assert a complete parent-death guarantee. Launch and observation calls have deadlines; success requires the real report, not merely a workflow definition or completed compile step.

The first full matrix run began at commit `34ead9b` ([run](https://github.com/krazyjakee/21x/actions/runs/38272178462)). Its results must be reviewed per target; later retries may use newer commits, and their provenance must remain separate. Cross-platform native validation was delegated to hosted runners rather than installing SDKs or performing heavy builds on the local HDD.

## Runtime redistribution notices

`scripts/tauri-resource-notices.mjs` preserves the complete Node 22.23.2 LICENSE, including embedded third-party notices, using the official release source and a checked SHA-256. It inventories every package/version/license declaration and actual notice file in the staged dependency tree; the inventory is bundled at `service/THIRD_PARTY_NOTICES.json`. The packaged smoke verifies that both the Node notice and the dependency inventory survived packaging.

The inventory deliberately records redistribution review as incomplete. `@anthropic-ai/claude-agent-sdk` has a proprietary notice referring to [Anthropic legal agreements](https://code.claude.com/docs/en/legal-and-compliance); that page permits unmodified preinstallation subject to commercial terms and end-user authentication conditions. The SDK's package declaration is not an MIT grant. `@opencode-ai/sdk` declares MIT but its pinned npm package contains no LICENSE file, so upstream notice preservation remains a review item. Passing import probes does not resolve these distribution conditions. Retain original notices and settle D1/release distribution policy before publishing a migration release.

### First matrix failures and bounded retry diagnostics

The first macOS x64 package loaded its GUI and passed SQLite, worker, SDK imports, navigation restriction and shutdown, but failed the PTY probe. The pinned node-pty archive contains Darwin `spawn-helper` files without executable bits; [Microsoft's upstream issue](https://github.com/microsoft/node-pty/issues/850) documents that packaging defect. Staging now grants executable bits only to regular helpers contained within its isolated service tree. Native preflight runs before GUI compilation and PTY failures expose only fixed phase names, a whitelisted errno, numeric exit metadata and marker/data counts.

The initial Windows package compiled and installed but failed engine initialization. Rust's canonical Windows paths use the extended `\\?\` namespace; the Node script resolver has a [documented compatibility issue](https://github.com/nodejs/node/issues/62446) with these paths. The host now converts canonical drive/UNC paths to Node-compatible paths **after** checking canonical containment, retaining Unicode through UTF-16. This is a targeted suspected-cause fix pending the installed Windows retry, not a confirmed successful result. Startup failures now record fixed stage/code metadata in the opt-in debug report; dependency stderr remains discarded. AppImage retries enable verbose bundler output to preserve the actual linuxdeploy diagnostic rather than infer a cause from its generic failure message.

## Owned process supervision (T05 preparation)

The supervisor now assigns the private Windows Node service to an unnamed, noninheritable [Job Object](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) with kill-on-close before sending initialize. Ordinary descendants inherit that job; assignment failure closes startup rather than continuing without ownership. Closing the host's last job handle covers abrupt host termination. This is implemented but awaits the Windows target tests; successful Linux tests cannot prove Windows Job behavior.

Unix starts the service in its own process group. Before reaping its leader, `waitid(WNOWAIT)` observes exit while retaining PID ownership; cleanup grants bounded SIGTERM grace, then signals only that owned group with SIGKILL and reaps the direct child. An observation failure disarms group signalling rather than risk a recycled PID. Linux also installs a parent-death SIGTERM before exec and checks the parent again to cover the installation race. Known service workers watch IPC loss; stdin EOF and signals retain known PTY/worker ownership until real exit callbacks, then escalate after 500 ms. Native handles have a final two-second service exit deadline.

The private `native-fixture-tests` feature enables staged Rust fixtures for service crash with a pending request, forced disconnect, and abrupt death of a separate Rust fixture host. Windows uses deliberately stubborn worker/grandchild fixtures to exercise job closure; Unix abrupt-death fixtures exercise cooperative stdin/IPC cleanup. Other tests exercise Unix process-group cleanup of stubborn descendants. Fixtures are opt-in, use a temporary profile, and their service operations are absent unless the supervisor explicitly injects its private test flag; the normal host clears inherited environment and never enables it. Tests observe exact recorded child PIDs and never terminate unrelated names or PIDs.

The packaged target workflow runs unit and staged supervisor tests before its GUI build using the same Cargo target and one job. Status reports actual direct-child wait completion as `ownedChildExited`. There is no restart or mutation replay. Unix descendants that escape the process group, hostile native addons, and persistent PTY shells outside the tiny feasibility probe do not have a generic process-tree guarantee from this work. Target reports and T05 production integration remain required.

Static API review checked the exact locked crates: Tokio 1.53.2 exposes the Windows process `raw_handle`; windows-sys 0.61.2 supplies the Job APIs with the enabled Security/Threading feature gates and pointer-compatible handles. Both selected Windows runner/application OS generations support nested jobs, and this job adds no UI limits or breakaway permissions. Darwin libc 0.2.190 exposes `waitid`, public `siginfo_t.si_signo`, and `WNOWAIT` for both selected architectures; process-group setup uses the stable Rust Unix command API. Linux parent-death signalling is scoped behind its target cfg. These checks assess source compatibility; target compilation and fixture results remain the evidence gate.

Linux's parent-death signal refers to the creating thread, as documented by [Linux man-pages](https://man7.org/linux/man-pages/man2/PR_SET_PDEATHSIG.2const.html); the host's runtime workers must remain alive for the service lifetime. Synchronous addon calls can delay JavaScript EOF/signal callbacks and its exit timer. Host-owned process-group force still covers ordinary members while the host lives; after abrupt Unix host loss, this implementation relies on the exercised service/worker cooperation. Windows job close provides the separate kernel ownership path.

Debug AppImage packaging explicitly sets `NO_STRIP=true` to preserve staged standalone Node and addon bytes through linuxdeploy. Verbose logs remain enabled. This is a packaging integrity choice for the feasibility artifact, not a confirmed diagnosis of the initial generic linuxdeploy failure; the installed/extracted retry remains the acceptance evidence.

## Synthetic desktop database prototype (G2 preparation)

The `synthetic-desktop` Cargo feature selects the fixed bundled `resources/service/database-stdio.mjs` entry. The renderer cannot choose an entry, resource root, profile, native principal or transport. Startup injects `TWENTYONEX_DATABASE_MODE=synthetic-only` and allocates a fresh host-owned temporary `21x-database-service-*` directory (mode 0700 on Unix). Ordinary feasibility builds keep `feasibility.mjs`; `desktop_invoke` returns `UNKNOWN_OPERATION` there. The experimental app identity remains separate from Electron and no existing profile is opened. The synthetic directory is removed after normal host shutdown; abrupt termination may leave synthetic files in the OS temporary directory.

`desktop_invoke` accepts only `{operation,payload,engineEpoch}` from the trusted `main` origin and forwards 14 named database operations: task list/get/create/update/delete, project list/get/default/create, three settings operations and transcript snapshot/delta reads. Settings are limited to three synthetic UI keys. Task creation cannot start agents, and task updates cannot change lifecycle, agent or source fields. Rust mirrors the shared database codecs with exact object keys, bounded text/arrays/depth, projected task/project/transcript shapes, and `OptionalResult` preservation. Native authority and unsupported operations remain separate from renderer codec checks. There is no renderer-facing transcript ingest, agent approval, shell operation or arbitrary callback.

Real service event envelopes are validated for version, adopted epoch, the five permitted event payloads and a per-desktop sequence beginning at one. Duplicates are ignored; malformed current events or sequence gaps disconnect the service. Stale well-formed envelopes are ignored. The host emits the complete frame on `desktop:event` only to `EventTarget::WebviewWindow { label: "main" }`; it does not broadcast to the application. The capability grants local main listen/unlisten and the restricted invoke commands, with no renderer event-emission permission. Native input frame/pending limits remain in force; this prototype has no renderer acknowledgement protocol for bounding Tauri's downstream event queue.

The debug synthetic smoke waits for the bundled `__TWENTYONEX_DATABASE_SMOKE__` runner, permits one real renderer reload, validates its exact 13 Boolean receipt fields, attempts denied remote navigation and closes the native window. Its twenty-second monitor records task create/edit/event observations, project creation, a missing optional result, persisted synthetic setting, transcript read APIs and reload rehydration. It skips the feasibility-only native probe. These receipts describe a database slice, including reads of an empty transcript; they do not establish real agent streaming, approval round trips or complete G2 parity. Release builds cannot enable this diagnostic from the environment.

A separate opt-in staged Rust test runs the actual synthetic service through the supervisor and checks task create/update/get, emitted event order, missing results, project creation, settings, real fixture projection snapshot/delta and direct-child exit. Its fixed native fixture ingress remains absent from the renderer allowlist. After staging the fixed service and native SQLite, central validation uses `cargo test --locked --manifest-path src-tauri/Cargo.toml -p twentyonex-engine --features synthetic-desktop -- --test-threads=1`, followed by the same command with `TWENTYONEX_TEST_RESOURCES` and `--ignored staged_synthetic_database_roundtrip_emits_real_target_events`. GUI compilation uses `--features synthetic-desktop`; source/schema inspection alone is not native GUI evidence.

The second Windows matrix attempt stopped before native preflight: notice inventory rejected a linked staged package. Its native build log referenced repository pnpm addon paths during rebuild. Native preparation now sets npm's cwd/prefix to the isolated service, clears inherited package/lifecycle/workspace context, explicitly chooses nonworkspace hoisted installs, verifies physical contained direct packages, and refuses native resolution outside that staged tree. Cache/proxy configuration is retained. Notice failures identify only the relative staged package name; linked trees remain rejected. A Windows retry is still required to confirm installation and packaged GUI behavior.
